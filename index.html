The idea

“We solved this last year.”
Did we keep the useful bit?

You find the old ticket. There’s a link to a dead dashboard, a screenshot, and a comment that says “fixed.” So you start digging. Again.

Some work leaves us better equipped for the next round: a failure we can reproduce, a decision we can explain, a boundary that lets us change one thing safely. We call that engineering capital.

But keeping things is only the beginning.

Accumulation

You kept something.

The debugging script made it into the repository. Good. Now it has a chance to help.

A return

It helped again.

Someone runs it during the next release and catches a regression. The script has earned a return.

Compounding

It made more possible.

That script becomes part of a harness that makes a difficult migration worth attempting.

*

This is a possibility to investigate, not a growth curve to promise. Tests go stale. Tools need repairs. A smaller codebase can be a better investment than another clever tool. Look for evidence in the next change.

A small, runnable example

Two deliveries.
One payment.

A payment notification arrives. Then the same notification arrives again. The invoice records two payments, and someone gets an interesting afternoon.

Keep the bug on a short leash.

The fix remembers which events it has already applied. The useful thing to keep is the tiny scenario that made the bug undeniable: an unpaid invoice, one payment event, and two deliveries.

With that case in the repository, the next engineer can make the old bug happen on purpose. “I think this still works” becomes a check they can run.

Investment retrospective
What this little demo doesn’t establish

The payment check covers sequential duplicate delivery in memory. Concurrent workers, restarts and durable storage need their own evidence. The invoice examples use integer minor units in one currency, without tax, proration or exchange rates. The lab demonstrates techniques; it does not measure a team’s returns over time.

Habits worth keeping

A few things
to work by.

Try one on the task you already have open.

Leave a useful trace.

Keep the test, explanation or small tool that would have saved you the investigation. Put it where the next person will look.

What software should remember
Know why the check is green.

A passing test is useful when you know what it establishes. Ask what could still be wrong. The author and the reviewer can share a blind spot; so can a model and the tests it wrote.

Knowing what constitutes convincing evidence
Keep learning in the work.

Predict what will happen, try it, and explain the surprise. If an agent writes the code, someone still needs to understand the system well enough to change it again.

How engineers become engineers
Try before you commit.

Build a small experiment while the decision is still cheap. You can learn more from two awkward prototypes than from a long argument about the perfect design.

Competing prototypes
Make it earn its keep.

A tool with no users is still something to maintain. Notice what helps, repair what misleads, and retire what has outlived its purpose. Deletion counts.

On your next change

Leave the next person
a better starting point.

Before you start, see what the last person learned. While you work, keep the evidence that settles the difficult bit. Before you finish, ask what is worth leaving behind.

Then watch what happens when someone uses it. That’s where the next lesson is.
