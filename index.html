The idea

“We solved this last year.”
Did we keep the useful bit?

You find the old ticket. There’s a link to a dead dashboard, a screenshot, and a comment that says “fixed.” So you start digging. Again.

Some work leaves us better equipped for the next round: a failure we can reproduce, a decision we can explain, a boundary that lets us change one thing safely. We call that engineering capital.

Compounding

It helped build the next check.

The saved input and expectation become the starting point for a recovery check. Compounding is the claim that the earlier work makes this new capability cheaper or more effective to build.

*

This is a possibility to investigate, not a growth curve to promise. Tests go stale. Tools need repairs. A smaller codebase can be a better investment than another clever tool. Look for evidence in the next change.

Where to invest

What holds
useful work up?

Suppose AI could prepare ten times as many changes tomorrow. How many could your team finish? Where would the others wait?

A billing change can be ready for review while nobody knows which cancellation rule it should follow. Another agent can produce another patch. The missing decision still needs to be made.

Eliyahu Goldratt’s Theory of Constraints helps us choose where to invest. Name the outcome you want. Find what limits it. A faster step is not necessarily a faster result.

  1. Identify: follow recent changes and find what actually holds them up.
  2. Exploit: make better use of existing capacity before building more tools.
  3. Subordinate: direct the rest of the work toward finishing valuable changes, not starting more.
  4. Elevate: if the constraint remains, try the smallest investment that can change it.
  5. Repeat: check the outcome, the costs and what limits the work now.

Keep a reviewed billing case if it helps the next engineer settle or verify a change. If the missing decision has not been made, make it first. If the case later makes a new recovery check cheaper to build, investigate that compounding effect separately.

Do not bypass necessary checks or sacrifice sustainable working hours. Some investments protect against future harm rather than increase current delivery capacity.

Whether we can reach 10× remains an open question. Look for evidence of improved outcomes, not just more generated code or faster local steps. Count review, rework and upkeep, and notice where waiting or risk moves.

How to judge a replacement
What these examples establish

The browser demo covers sequential duplicate delivery in memory. The separate Python walkthrough adds simulated restarts and interruptions at named points in temporary local storage. Neither establishes behavior under concurrent workers, machine failure or a real payment provider’s contract. Reusing the cases demonstrates a connection between capabilities; it does not measure whether the investment saves a team time.

Habits worth keeping

A few things
to work by.

Try one on the task you already have open.

Leave a useful trace.

Keep the test, explanation or small tool that would have saved you the investigation. Put it where the next person will look.

What software should remember
Know why the check is green.

A passing test is useful when you know what it establishes. Ask what could still be wrong. The author and the reviewer can share a blind spot; so can a model and the tests it wrote.

Knowing what constitutes convincing evidence
Keep learning in the work.

Predict what will happen, try it, and explain the surprise. If an agent writes the code, someone still needs to understand the system well enough to change it again.

How engineers become engineers
Try before you commit.

Build a small experiment while the decision is still cheap. You can learn more from two awkward prototypes than from a long argument about the perfect design.

Competing prototypes
Does someone need to start this every time?

When a recurring procedure is understood and can be checked, try making it run when the work arrives. Keep the decisions and exceptions that need someone’s judgment.

Automating the work of engineering
Make it earn its keep.

A tool with no users is still something to maintain. Notice what helps, repair what misleads, and retire what has outlived its purpose. Deletion counts.

An adoption guide for teams and leaders

Make room for
the next improvement.

One team builds a useful check. Another team still needs the original specialist to use it. Who pays for making that handoff work, and what happens when delivery pressure returns?

Start with one recurring job, a bounded investment and a decision about what to keep. Use ordinary planning and retrospectives rather than introducing a new improvement program.

Proposed comparison · not yet run

Does the next check cost less?

The protocol compares building a new verification capability after deliberately retaining a reusable scenario or following ordinary development practice. It counts effort, quality, the initial investment and failed attempts.

Still to establish: whether that connection helps under a fixed budget. The public walkthrough is teaching material, not a hidden benchmark.

For a working team, follow one recurring kind of change for twelve weeks. Record bypasses and upkeep as well as useful runs. A decision to shrink or remove the tool is a useful finding.

On your next change

Leave the next person
a better starting point.

Before you start, name the useful outcome and what is holding it up. While you work, keep the evidence that settles the difficult bit. Before you finish, ask what is worth leaving behind and where the next investment would matter.

Then watch what happens when someone uses it. That’s where the next lesson is.
