Enough detail to make a decision

Use this for a bet that needs a planning conversation. A small fix inside an ordinary task can stay small. The questions are prompts, so leave out what you do not need and copy the note into the issue you already use.

Follow the work from the initial need to a useful result. Which steps can disappear? Which can run automatically? What would a different interface, decision rule or division of work make possible? Automating the work of engineering develops these questions beyond the time spent writing code.

Your entries stay in this page and are not sent anywhere. Copy them before leaving; this worksheet does not save a draft.

Read a worked example

This hypothetical product team waits for a platform engineer to prepare and later remove a preview environment for each experiment. The proposed change removes that request queue: eligible branches receive an isolated environment automatically, with a cost limit and an expiry. Existing deployment templates and synthetic data provide a starting point.

The team sets an illustrative two-day build cap, half a day for adoption and a review after five eligible experiments or twelve weeks. It follows the whole experiment: time to a usable product decision, human interventions, failed provisioning, cleanup and total cost. A fast environment is useful only if it helps the experiment finish.

Recovered platform time goes toward the next constraint. The same provisioning and cleanup machinery might later let agents investigate alternatives independently. That is a separate investment to evaluate; storing the templates or using them again does not establish compounding.

The proposed investment

Name who benefits, what they can accomplish and the conditions it covers. Describe the result beyond the automated task.

Follow a recent case through waiting, decisions, execution and follow-up. Name another plausible cause and any step or handoff that could disappear.

Include knowledge, decisions, interfaces, automation and access. What would need adapting before people or agents could use them independently?

Specify what you will remove, redesign or automate in one bounded experiment. What starts the work, what lets it finish, and which exceptions still need a person?

What is its main purpose?

State the prediction and quality bar. Measure time to the outcome, total human attention and economic cost, including failed attempts, upkeep and work shifted to others.

Name a later capability, what it could reuse and how recovered capacity could help build it. Leave this blank if the immediate return is enough.

Name the owner, users and authority to change the workflow. Include build, adoption, oversight, compute, upkeep and the work displaced.

Set a review trigger and a date in case the expected work never arrives. Say what would justify stopping.

Come back after the workflow runs

Add what happened to the same issue. Was the useful outcome achieved? Which recurring tasks or handoffs disappeared, and where did people still need to intervene? Check whether the constraint was removed or moved elsewhere. Then decide whether to keep, simplify, repair or retire the investment.

If a later capability is built, record what it inherited, the new work required and where recovered capacity went. That is where the compounding claim can be tested. A useful immediate return needs no larger story.
